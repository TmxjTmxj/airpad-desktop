# AIRPAD 已知限制

本文档列出**尚未验证、已失效、或有意不做**的部分。原则：没有实测的项目写明"未测量"，不把"代码写了"当成"功能可用"。

最后更新：2026-09-12。本轮在 DeepSeek 版本之上继续收尾；下面 §A0 是此前保存的开发记录，不代表所有实机测量在本轮重新执行。当前交付与验证以 README 和 `RELEASE-COMPLETION-PLAN.md` 为准。

本轮补充：应用内五阶段手型测量、Windows 自包含 EXE、丢失后旧捏合取消、持续拖拽、输入暂停恢复与交付素材边界。真人点击精度和疲劳数据仍待采集。

## A. 验证缺口

### A1. 真实桌面输入：已在自建靶场验证，仍有边界

已完成（见 §A0）：点击、拖拽、滚轮、`Ctrl+滚轮`、租约到期释放、真实急停、持有按键时的进程崩溃恢复，全部在真实 Windows 会话中、对**本工具自己的可见窗口**注入并核验。

**仍未验证**：

- 在**第三方应用**（浏览器、资源管理器、Office、CAD）中收到的输入是否正确
- 多显示器、负坐标、125% / 150% 混合 DPI 下的相对位移
- 账户权限不足（UIPI）导致 `SendInput` 被拦截时的表现（代码会报错并暂停，但未实测）
- 锁屏 / 休眠 / 切用户 / 显示器插拔时的释放与 epoch 作废
- 长时间（1 h / 4 h）反复注入-释放循环是否累积残留

### A2. 无真人可用性数据 ⚠️ 最高优先级

- **手部识别阈值尚未在真人手上验证**：伸指分数、滞回参数、捏合 0.42/0.62 都是**移植花绳原型 + 按合成手模型推导**的，没有在你的手、你的光照、你的距离下测过。这是当前最需要关闭的一条，工具已就绪（`tools/hand_check.py`，会输出各手指分数与 pinch 分布）。
- 点击精度 / 召回（规范要求 ≥100 次明确意图点击的统计）：**未测量**
- 无意图误触率：**未测量**
- 拖拽空程是否自然（规范提到的 180 ms 起拖初值主观评估）：**未评估**
- 20 分钟连续使用成功率与疲劳（MVP 门槛）：**未测量**
- 规范要求的 ≥5 人工程筛查、≥12 人候选测试：**未进行**

当前提供可运行的开发版本。应用内校准已替代必须运行 `hand_check.py` 的首次使用路径；完成自己的校准不等于已经取得真人可用性评估数据。

### A3. 环境矩阵极窄

- 只测过**一台相机（设备 0）**、一种光照与背景
- Windows 10 与 11 的差异、普通用户 vs 管理员权限：未测
- 断网运行、1 h / 4 h 稳态：未测

### A4. 端到端延迟未测

已测的只有内部推理延迟（p50 8.4–15.8 ms）与纯算法单步耗时（p50 3.7 µs）。**相机 → 光标实际可见响应**的端到端延迟未测量，而这才是用户能感知的数字。

### A5. 设计规范里的分阶段 CLI 入口未提供

规范写的 `airpad camera --preview`、`airpad track --preview`、`airpad pointer --backend mock --practice`、`airpad run --mode pointer-only` 等**分模式入口并未实现**——功能合并进统一 GUI（练习模式替代了 `--backend mock --practice`）。替代路径：`tools/camera_probe.py`、`airpad run --start-camera`、`tools/replay_smoke.py`、`airpad replay`。

`airpad replay` 现在同时接受 **landmark 观测**（走真实几何门与手选择）与旧的 HandSample 行，因此回放验证的是识别链而不是它的输出。

## B. 有意的技术限制

### B1. 物理输入抢占存在竞争窗口

物理状态检查与 SendInput 提交之间存在 check-to-submit 间隙；且 Windows 对同一按键不维护"合成/物理"两套独立所有权。因此**你手工按下的相关键可能干扰 AIRPAD 的一次注入**。用一个原生批次提交"按下+动作+抬起"消除了调用间的交叉窗口，但没有消除所有物理重叠情形。

### B2. 账本协议不支撑重启或多 owner

共享账本使用按字节的写前所有权，前提是 **每个 `BrokerClient` 只有一个不重启的子进程**。父进程恢复时会等待该子进程确认死亡后再串行化写入。若将来需要可重启 / 多 owner 的 Broker，必须重新设计账本协议并单独验证。

### B3. 没有独立的 UI 心跳协议

父进程死亡由 worker 每轮循环检查；失去新鲜观测的 UI 会在 150 ms 租约后失效。规范里提到的"独立 1 秒心跳"**没有实现**。后果：UI 假死但进程仍活着的场景靠租约兜底而不是靠心跳。

### B4. 延迟阈值是策略值，不是硬实时保证

80 ms 观测上限、150 ms 租约、250 ms 无进展撤销都是策略阈值与调度目标。**已经在执行的 native 调用无法被撤销**——门禁只阻止后续未授权的调用。实测到的 150–155 ms 租约释放是该策略在**这台机器当前负载下**的表现，不是上界保证。

### B5. 单目手部跟踪的固有模糊

手部距离是投影量，会混入前后深度与视角变化。双手进入画面、交叉、遮挡时身份关联会主动拒绝（`Hands overlap` / `Ambiguous hands`）而不是猜测——代价是那些姿态下**不可操作**。

### B6. 滚动/缩放消歧仍是启发式

规范要求"双指混淆 ≤2%" 才允许 Zoom 默认开启。这个门槛**没有实测数据**，因此 Zoom 保持 **Experimental / 默认关闭**。

### B7. 三指动作可能被吞

三指滑动有 0.65 s 时间窗与 0.6 s 触发后锁定，快速连续滑动时第二次可能落在锁定窗口内而**不触发**。

### B8. 低帧率保护可能反复触发

处理帧率在足够观测窗口内低于 12 FPS 时释放控制；独立的 80 ms 观测门限仍然生效。弱光、相机被占用、CPU 高负载时可能出现"能跟踪但控制被反复暂停"的体验。

### B9. 单手 only

双手模式、Mode Hand 语义、3D orbit/pan/zoom、Blender / SolidWorks 适配**全部未实现**。

### D3. 进度追踪此前未维护（已修复）

### D4. fixture 是脚本生成的，不是真人录制

`tests/fixtures/landmarks/pointer.jsonl` 由 `tools/hand_model.py` 合成，文件头 `source: synthetic-scripted` 明确标注。它验证**几何门、手选择、状态机与整条装配链**的确定性，**不**验证识别器在真手上的准确率。要验证后者需要录制真人 landmark，而那需要操作者明确同意。

### D5. 早期版本的识别阈值过严，导致"根本用不了"（已修正）

用户实测反馈：手能出画面，但软件不响应。对照花绳（`D:\codex\花绳`，一套在同一手上工作正常的 MediaPipe 应用）逐项核对后，确认是四个判定层面的缺陷，而非相机或模型问题：

| 缺陷 | 早期实现 | 修正后 |
|---|---|---|
| 采集分辨率 | OpenCV 默认 **640×480** | 主动请求 **1280×720**（帧率不变，关键点精度显著提升） |
| 伸指判定 | 关节内角 `pip>150° 且 dip>135°` **硬判定** | 连续 0–1 分数（距离比 + 直线度）+ 每指**滞回稳定度** |
| 姿势要求 | 必须精确 `[伸,蜷,蜷,蜷]`，中指半伸即 `unknown` → 完全失控 | 逐指分数判定；两指/三指另行要求 ≥0.75，半蜷中指不再抢走指针 |
| 捏合阈值 | `0.23` 掌尺度（约为花绳验证值的**一半**，真手捏不到） | `0.42 / 0.62`（花绳同量级） |
| 接管方式 | 必须先开掌 3 帧 ≥0.12 s，再保持食指姿势 3 帧 ≥0.12 s 才"武装" | 食指伸展即接管，基线当帧归零 |
| 几何门禁 | 整手必须在 ±3% 边距内、掌宽/掌高比硬限制 | 边距放宽到 ±12%，去掉比例硬拒绝 |
| 默认模式 | 练习模式 + 需手动 Enable | **默认即控制桌面** |

**这是工程缺陷的修正，不是"已经验证可用"**：新阈值在合成手模型上通过了测试与端到端冒烟，但**仍未在任何真手上验证**。必须先用 `tools/hand_check.py` 取到真实分数分布，才谈得上"认得你的手"。

### D6. 滞回衰减常数写错，导致开掌后指针"卡住"（已修正）

移植花绳的滞回时，我把"低于 0.45 分"的衰减从原来的 `-0.16/帧` 写成了统一的 `-0.05/帧`。后果：张开手掌后拇指分数掉到约 0.14，但要**20 帧（0.67 秒）**才退出"伸展"状态，于是姿势一直是 `open`，状态机一直停在 `CLUTCH`——**开掌后指针要等 0.7 秒才回来，拖拽动作被整个错过**。

发现方式：`tools/replay_smoke.py` 走的是实时滞回路径，而 `airpad replay` 当时走的是无状态路径，两者结果不一致——实时路径下拖拽完全没有发生。这条差异本身就是缺陷信号。

修正为分档衰减（`airpad/geometry.py`）：

| 分数区间 | 增益 | 含义 |
|---|---|---|
| ≥ 0.62 | +0.36 | 明确伸直，快速进入 |
| 0.45 ~ 0.62 | 未伸展 +0.20 / 已伸展 −0.06 | 放松的指点手指：约 4 帧（0.13 s）接管，已伸展时缓慢退出 |
| 0.30 ~ 0.45 | −0.10 | 模糊区间，防止抖动翻转 |
| < 0.30 | −0.30 | 明确蜷起：约 4 帧退出 |

同时把 `airpad replay` 与 fixture 测试都改为走**实时同一条滞回路径**，否则回放验证的是一条应用从不执行的管线。修正后实时路径与参考路径的动作序列完全一致（点击 / 拖拽 / 滚动各就各位）。

### D7. 姿势分类存在空档：中指分数 0.62–0.75 会导致控制被释放（已修正）

`classify_pose` 原来的分支是：先判 `two`（要求中指分数 ≥0.75）、再判 `three`，最后 `if index and not middle: pointer`，否则 `unknown`。于是当中指**滞回判定为"伸展"（分数 ≥0.62 持续 2 帧）但分数还没到 0.75** 时：

- 不满足 `two`（分数不够）
- 也不满足 `pointer`（`middle` 为真）
- → 落到 `unknown` → 状态机判定为不可用姿势 → **释放全部输入并回到 Clutch**

也就是说，一根停在 0.62–0.75 区间的中指会让控制在"能用"和"完全断掉"之间反复横跳。这是"用不了"的第三个独立成因。

修正后的规则：**只要食指处于伸展状态，姿势永不返回 `unknown`**——`two`/`three`/`open` 只有在"明确"时才抢占，其余一律是 `pointer`。回归测试 `test_an_extended_index_never_yields_an_unusable_pose` 会把中指分数从 0.00 扫到 1.00，断言结果只可能是 `pointer` 或 `two`。

发现方式：为"按自己的手定阈值"写单元测试时，随手构造了一组 `middle=0.70` 的分数——测试立刻失败。

### D8. Windows 单调时钟的分辨率会让快速相机"看起来像"重复观测（已加保护）

`time.monotonic()` 在 Windows 上按 ~15.6 ms 的刻度前进。若相机帧率高于该刻度（60fps 已接近，120fps 必然），两帧会拿到**完全相同的时间戳**；状态机把"时间戳不前进"当作重复观测——这是刻意的失效保护（重复观测不能续租、不能续动作）——于是会持续释放输入。

- 现实影响：**30fps 的相机不会触发**（帧间隔 33 ms ≫ 15.6 ms）。本项目的采集与 fixture 都是 30fps。
- 已加保护：`airpad/vision.py` 在采集循环里保证时间戳严格递增（重复或回退时用 `上一次 + 1 ms`），并加单元测试。
- 发现方式：一个运行时行为测试偶然间歇性失败（10 次里错 1 次），追下去发现是**测试自己的帧间隔（10 ms）低于时钟分辨率**，而不是产品缺陷；顺手把这个真实边界也堵上了。

同一个坑在真实输入探针里也遇到过（`tools/windows_input_probe.py` 的观测时间戳必须严格递增，见该文件的 `now_obs()`）。

### D9. 阈值推导在"空档窄"时等于没修（已修正，两处）

新增"按自己的手定阈值"后，我给它写了两个边界测试，结果连续暴露两处逻辑缺陷——**都是会让低分手继续用不了的**：

**D9a：空档窄于 0.18 就退回内置默认 0.62。**
可一个分数本来就偏低的手（伸展中位 0.52、蜷起中位 0.40）恰恰是默认值最不适用的情况——退回默认等于白测。
修正：只要两个姿势的中位数**可区分**（差 ≥0.05）就照常测，把阈值放在两者中点，并在报告里标 `confidence: narrow`（`narrow_fingers` 列出是哪几根）——诚实标注"这次推导余量小"，而不是假装没测过。

**D9b：模糊区间按阈值比例缩放，会把蜷起姿势吞进去。**
模糊区间原来固定取阈值的 72.6%。阈值降到 0.46 时，模糊区间起点变成 0.334——而这只手**蜷起时就是 0.40**，落进模糊区间后每帧 +0.20，4 帧后照样被判成"伸展"。**一握拳反而开始指点**。
修正：模糊区间改为锚定在这只手**自己的蜷起中位数之上**（`low + 0.15×(high−low)`，窄空档用 0.25），不再单纯按阈值比例推。Profile 新增 `finger_marginals` 字段存这五个值（null 表示按比例回退），JSON 往返与校验都有测试。

发现方式：两个测试分别写出来立刻失败（第一个失败是因为**测试断言写错**——滞回本就需要 2–4 帧才置位，我在每帧都断言了；第二个失败是真正的设计缺陷）。这两处修正后，一个"伸展 0.52 / 蜷起 0.40"的窄空档手也能被正确区分。

### D10. 开掌要求拇指伸展 → Clutch 会静默失效（已修正）

`classify_pose` 原来判定 `open` 的条件是"四指 + **拇指**全部伸展"。可人张开手掌时，拇指经常是**并拢贴在掌侧**的；而且拇指是最不可靠的关键点（4 个子分数、几何上经常被遮挡/透视压缩）。

实测（合成手模型）：拇指伸开时分数 **0.928**，拇指并拢时只有 **0.480**——低于 0.62 的阈值。于是 `open` 落空，姿势落到 `pointer`：**你想"张开手掌 = 松手"，光标却继续跟着动**；拖拽中想松手也一样失效。

修正：`open` 只要求四根手指。回归测试同时覆盖两侧——拇指并拢的开掌必须判成 `open`，而拇指并拢的**指点**姿势不能被误判成开掌（否则指针会一直处于 Clutch）。

### D11. 输入进程首次握手失败就关掉整个会话（已修正）

`BrokerClient.enable()` 会给工作进程 2 秒完成握手（建 ctypes 边界 + 注册急停热键）。实测正常耗时 **~98 ms**（10 次采样 92–99 ms），但全量测试负载下偶发超时一次。而当时运行时的反应是：

```python
else:  # enable 失败
    self.set_enabled(False); self._show_error('Input broker is unavailable')
```

**一次瞬时调度饥饿 = 整个会话被关掉，用户得手动再点 Enable**。修正：失败时先重试（最多 3 次），只在连续失败后才报错停止；握手期限从 2 s 放宽到 3 s（正常路径不受影响）。两个方向的测试都有：瞬时失败必须自愈，持续失败必须停止并报错。

### D12. 模型下载失败会留下残留文件（已修正）

到第 8 轮为止，测试集中在识别、状态机、输入层；`airpad/resources.py`——**整个项目唯一联网的代码**——从没有被测过。补测试时立刻发现：

```python
if total>20_000_000: raise ValueError(...)   # 超限：直接抛，临时文件留在磁盘上
```
原来的清理只覆盖"哈希不匹配"一条路径。所以**下载超限**或**连接中途断开**都会在 `models/` 下留下一个 `hand_landmarker.download` 半成品。

修正：把下载+校验整体包进 `try`，任何失败路径都删除临时文件再抛出。

**验证方式**：把修复临时回退后重跑，新测试中 2 项立刻失败（断言 `.download` 不存在）；恢复修复后 8 项全过。这证明测试不是空过的。

补充覆盖：哈希不匹配必须拒绝且不留文件、已存在合法模型时**绝不发起网络请求**（离线可用性）、`doctor` 命令不联网、URL 必须是 https。

### D13. 日志关闭不可重复调用（已修正）

`airpad/telemetry.py` 同样从未被测过，而它带着一条明确的安全声明（"诊断队列满不得阻止资源关闭"）。补测试时发现 `SessionLog.close()` **第二次调用会抛 `AttributeError`**（`QueueListener.stop()` 之后内部线程已置空）。

当前调用路径有 `_closed` 保护，所以运行中没暴露；但"托盘退出"与"关闭窗口"都可能触发清理，一旦重复调用，异常会**中断其后的清理步骤**——在关闭路径上抛异常是危险模式。

修正：`close()` 幂等。同时补上"队列满时 `event()` 必须立即返回而不阻塞"（实测 <50 ms）、非 ASCII 字段往返、日志轮转有界（2 MB × 3）等测试。

### D14. 测量工具收不到握拳数据，导致食指阈值永远测不出来（已修正）

到第 11 轮为止，我每次手动跑 `hand_check.py` 看到的都是 `phase_samples: {open: 0, fist: 0, ...}`——因为测试环境里没有手。**采集代码从来没有在有数据的情况下运行过**。第 12 轮给它加了 fixture 模式（脚本手走完五个相位），第一次带数据运行就暴露：

```python
if quality.get('valid'):          # 只有"有效姿势"才采集
    ...
    collected[name].append(...)   # 握拳是 valid=False → 永远不采集
```

握拳在几何门里是**刻意的无效姿势**（控制层必须释放），可它同时是"蜷起分布"的**唯一来源**。后果：

| 手指 | 蜷起分布来源 | 结果 |
|---|---|---|
| 食指 | 只有握拳 | **永远"样本不足" → 永远退回默认 0.62** |
| 拇指 | 指点 + 握拳 | 靠指点相位勉强可用 |
| 中指/无名指/小指 | 指点 + 握拳 | 靠指点相位勉强可用 |

也就是说：**这工具对于"分数偏低的手"——它存在的唯一理由——无法测出最关键的那根手指。** 用户会跑完测量，食指仍用着不适合的默认值，然后得出"还是用不了"。

修正：只要几何**算出了分数**就采集，与姿势是否可用无关（拒绝时的 quality 里本来就带着 scores）。

发现方式本身也值得记：我给"承诺链路"写的测试是**直接把合成分数喂给推导函数**的，绕过了采集——测的是推导，不是这条路径。

### D15. `app_is_running()` 在数据目录不存在时误判为"程序正在运行"（已修正，第 11 轮引入）

第 11 轮加的"程序运行时拒绝写 profile"保护用了 `QLockFile.tryLock`。但**锁文件无法在尚不存在的目录里创建**，于是 `--apply` 在第一次测量时（数据目录还没建）被误判为"程序在运行"而拒绝写入。

修正：检查前先创建目录。加了一项测试专门覆盖"数据目录尚不存在"这条路径——它正是首次测量的路径。

## D16–D19. 点击手势优化（第 12 轮）：四个让点击失真或消失的缺陷

用户反馈"手势点击等做的不是很好"之后，按 TriPad（ACM CHI 2024）、PinchCatcher（arXiv 2503.05456）与 Apple Vision Pro 的公开描述重做了点击路径。**结论：不是参数没调好，是判定信号用错了**，另外还有两条死代码与一条缺失的姿势约束。四条都由测量（`runtime-data/pinch_*.py` 探针）定位，不是推理出来的。

### D16. 判定用了平滑后的 pinch 值，而阈值是从原始值量出来的 —— 点击**全部**失效（已修正）

我把 One Euro 滤波加在 pinch 信号上，然后拿滤波值与阈比较。滤波在**跳变沿**必然滞后（无偏只对平稳信号成立），实测：

| 帧 | 原始 pinch | 滤波后 | 后果 |
|---|---|---|---|
| 手指已完全张开的那一帧 | 0.900 | 0.586 | 永远够不到 `pinch_release=0.62` → **释放沿丢失，click 不触发** |
| 捏到底持续 3 帧 | 0.180 | 最低只到 0.273 | `pinch_depth > pinch_contact(0.25)` → **接触深度门永远不满足** |

探针实测：2–15 帧各种快慢的捏合、保持 1–6 帧，**无一例触发点击**——即"点击完全不能用"。而 0.18 的实际接触深度说明手是捏到位了的，是软件在骗自己。

修正：**判定一律走原始 pinch**；抗噪改由"≥3 帧 + ≥60 ms + 接触深度≥2 帧"三重条件承担，不引入任何边沿延迟。探针复测：167 ms 快捏到 600 ms 慢捏**全部**在手指开始分离的那一帧出点击；擦到 0.26 永不点击、0.24 才点击（深度门精确分辨）。滤波值只留给界面读数。

### D17. `PINCH_APPROACH`（"收拢冻结"）是死代码（已修正）

```python
previous_pinch = self.previous_pinch      # 上一帧的值
self.previous_pinch = pinch               # 同一步里被覆盖成本帧值
...
if ... and self.previous_pinch - pinch > .005:   # 自己减自己，恒为 0
```

**恒等于 0**，所以这个分支从写下那天起从未执行过：文档承诺的"捏合期间指针冻结、点击不漂移"实际从未生效。之所以一直没暴露，是因为上面 D16 让点击先失效了，没人能观察到点击漂不漂。

修正：改用局部变量（真正的上一帧值），触发阈值从噪声级 0.005 提到 0.03（单帧真实收拢动作），避免在 release 带附近抖动就冻住指针。测试 `test_click.py::test_a_closing_pinch_freezes_the_pointer_before_contact` 与 `test_pointing_noise_does_not_freeze_the_pointer` 双向钉住。

### D18. 握拳会误触发点击（已修正）

捏合距离是"拇指尖-食指尖 / 掌尺度"，而**握拳时这两个指尖同样靠得很近**（都蜷进掌心）。原逻辑只在姿势为 `unknown` 时取消，握拳（`fist`，一个明确的"不可用姿势"）不在此列——于是"攥一下手想暂停"会在张开时补一次点击。

修正：捏合只能由**驱动指针的姿势**（伸着食指）发起；已在进行的捏合不受影响，所以捏得很紧、食指短暂被判为蜷起时不会半途丢失点击。测试 `test_click.py::test_a_fist_with_the_fingers_together_never_clicks`。

### D19. 按住真实鼠标键时只有"按键"被拒绝，光标移动仍然输出（已修正）

后端的物理键检查只挂在按下/和弦路径上，`move` 不经过它。用户按住真鼠标左键拖东西时，AIRPAD 的光标移动照发——**这正是"和用户的手抢鼠标"**。集成测试 `test_a_physically_held_button_is_never_fought` 断言"零后端事件"，本轮点击路径改变后它开始失败，暴露了这一点：以前只是脚本流程恰好没产生移动而已。

修正：物理指针键（左/右/中，用独立 VK 码，避免与"右方向键"混名）被按住且**不是 AIRPAD 自己按下的**（用 write-ahead 账本排除，否则拖拽会拒绝自己的移动）时，全部合成输入暂停。释放路径不受影响（`up` 永远不被门禁挡住）。

### D20. 接触深度写成绝对常数 0.25，换一只手就可能永远点不出来（已修正）

`pinch_contact` 初版是写死的 `0.25`。它与**默认**的 `pinch_close=0.42` 配套（0.25 已用探针验证能精确区分"擦过 0.26"与"捏到 0.24"），但它是个绝对量：校准向导把大捏合区间的手截断成 `pinch_close=0.60` 时，这只手可能根本捏不到 0.25 —— 结果是**一次点击都不会发生**，而界面上没有任何解释。这与 D16 是同一类错误：拿属于一种手的常数去判定另一种手。

反推本仓库那份 profile 的原始统计量（`release = closed + 0.75×spread`、`opened ≈ 1.24`）得到 `closed ≈ 0.92`，而 `pinch_close` 被上限截断到 `0.60`——即**阈值比这只手自己的闭合水平还低**，捏合永远不会触发。数据来自合成手的测试跑，不是真手，但它把两个缺陷都暴露了出来。

修正：
- 接触深度改为**跟随 close**：`pinch_contact = 0.6 × pinch_close`（默认 0.42 → 0.252，与已验证的 0.25 一致；close=0.60 → 0.36）。`Profile.load`、`Profile.updated`、校准向导、`tools/hand_check.py` 四条写入路径全部按此规则；旧 profile 缺该字段时**按它自己的 close 补齐**，不套默认值。
- 显式给出的接触深度仍然优先（`updated({...,'pinch_contact': x})` 不会被覆盖）。

### D21. 阈值截断会产出"永远跨不过去"的阈值；且浮点边界会让走完五个相位的校准在最后一步失败（已修正）

两处，都在推导侧：

1. `recommend_pinch` 把 `close` 截断到 `min(0.60, …)`。当一只手自己的闭合分位 `closed` 高于这个上限时，截断结果**低于它的闭合水平**——阈值存在、格式合法、但没有任何捏合能穿过它（D20 里那份 profile 就是）。现在的做法与 `derive_sensitivity`（横扫太小就拒绝）一致：**拒绝推导**并让调用方提示重做捏合相位，而不是产出一个看起来正常、实际永远不触发的阈值。
2. `pinch_contact <= pinch_close - 0.05` 这条校验在浮点下会误杀：`0.6 - 0.05 = 0.5499999999999999`，于是**恰好等于 0.55** 的合法深度被拒绝——用户走完五个相位后，校准卡在最后一步报"depth must be clearly deeper than close"。校验加 `1e-9` 容差（十进制上 0.55 与 0.5499999999999999 是同一个数）。

### D22. 测量工具会把"自己判定为不合格"的测量写进 profile（已修正）

`tools/hand_check.py --apply` 原来无条件写入。仓库里那份 `artifacts/hand-check.json` 就是活证据：

| 字段 | 值 | 含义 |
|---|---|---|
| `enough_data` | `false` | 工具自己说数据不够 |
| `hint` | "These phases collected too few frames: open." | open 相位只收到 **3** 帧 |
| `phase_samples` | `{"open": 3, "fist": 74, "point": 34, "sweep": 13, "pinch": 51}` | 五相里一相基本是空的 |
| `recommended.pinch` | `closed_p15 = 1.0077`，`open_p85 = 1.2107` | 所谓"捏合闭合"时拇指食指还隔着一整个手掌宽——这一相位根本没捏 |
| `applied` | `true` → `runtime-data/profile.json` | **还是写了**，并提示"Start AIRPAD to use these values" |

后果：写进去的 `pinch_close = 0.60` 比这只手自己观测到的闭合水平（≈1.0）还低，**没有任何捏合能跨过它**；同时 open 相位太薄导致五指阈值全是默认 0.62。这份 profile 从写下的那一刻起就不可能点出任何一次点击，而界面上没有任何提示——用户看到的只会是"点击做得很差"。

修正：`--apply` 先过 `apply_blocker()`——任一非 pinch 相位帧数不足（< 12）就**明确拒绝写入**，报告"什么都没写"以及要重做哪些相位；pinch 相位不参与这个拒绝（它有自己的回退：阈值保持不变）。这条 + D21 的不可达拒绝 + D20 的深度跟随，三条一起把"静默写出一份永远不触发的 profile"这条路径封掉了。

## E. 环境注意事项

- **`pytest` 默认临时目录可能不可用**：在受限环境下 `%TEMP%\pytest-of-*` 与仓库内 `.pytest_cache` 可能被拒绝访问，表现为 setup 阶段的 `PermissionError`。这不是代码缺陷，用可写的 basetemp 即可：
  ```bat
  .venv\Scripts\python.exe -m pytest tests -q -p no:cacheprovider --basetemp=.\runtime-data\pytest-tmp
  ```
- **子进程输出的编码**：若环境设置了 `PYTHONIOENCODING=utf-8` 而系统 ANSI 代码页是 GBK，子进程会写 UTF-8 而 `subprocess(text=True)` 按 GBK 解码，导致读取失败。`tests/test_cli.py` 因此显式指定 `encoding='utf-8'`；CLI 帮助文本也已保持纯 ASCII，避免在非 UTF-8 控制台上打印失败。
- **OpenCV 与非 ASCII 路径**：`cv2.imread` 无法打开含中文的路径，需用 `np.fromfile` + `cv2.imdecode`。应用自身不受影响（模型按字节读取、截图走 Qt）。
- **相机在沙箱内可能无法打开**：曾观察到沙箱内打开失败、沙箱外成功，据此定位为设备访问限制而非代码问题。
- **离屏 Qt 字体**：offscreen 平台下需注册系统字体，否则出现豆腐块；`ui.py` 已处理，真实桌面无此问题。
- **不要用 PowerShell 改本仓库的 UTF-8 文本**：`Get-Content -Raw` 会按系统 ANSI 代码页读取，`Set-Content -Encoding utf8` 再写回，中文会变成乱码**并丢失内容**。这是本仓库出现过的一次真实事故（README 被写坏后从交付包里的副本恢复）。改用编辑器/`edit` 工具，或在 Python 里用 `encoding='utf-8'` 显式读写。
